## Run it

```bash
# Node 22+
cd server && npm test && SUPER_ADMIN_EMAIL=you@yourcompany.com SUPER_ADMIN_PASSWORD=change-me-8-chars-plus npm start   # API on :8787 (SQLite file church.db)
cd app    && npm test && npm run serve       # app on http://localhost:5173
# optional browser walkthrough (needs python playwright + chromium):
#   DB_PATH=:memory: PORT=8788 node --no-warnings server/src/index.js &   then   python3 e2e/walkthrough.py /tmp
```
Open the app, choose "Register a new church", and go. To sign in to the platform admin console instead, open `http://localhost:5173/admin.html` and use the `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD` above (see "Platform admin console" below). To point at a hosted server run `localStorage.setItem('apiUrl','https://your-server')` in the browser console (or edit `app/js/config.js`) — this is a developer-only escape hatch now; the regular app no longer shows a "Connection"/server-address card in Settings.

**Seeing an old version after an update?** Make sure you replaced your whole local folder with the newly downloaded one (don't unzip on top of the old one — old files that were renamed or removed will still be sitting there). Then do one hard reload (Mac: Cmd+Shift+R). The service worker force-activates and reloads the page itself when it detects a new build, so a single hard reload is normally enough — you don't need to close every tab or manually unregister it anymore. Open the browser console and check for `The ChurchFlow build: v0.16.0 …` to confirm which version actually loaded.

## Platform admin console (super user)

`app/admin.html` is a separate, standalone page — not part of the regular church app's tabs/navigation — for the one person operating The ChurchFlow across every church (you). It's deliberately kept apart from every church's own accounts so a paying church user never sees it, can't reach it by clicking around, and a bug in the regular app can't expose it:

- **Separate login, separate table.** Platform-admin credentials live in their own `platform_admins` table (`server/src/db.js`), never in a church's own `users` table, and there is no sign-up screen for it. A platform-admin session token is tagged with a different `kind` than a church-user token, so the two can never be swapped: a stolen church-user token can't be used to reach `/admin/*` routes, and vice versa (`server/src/app.js`'s `auth()`/`authAdmin()`).
- **No public sign-up — set it from the environment.** On server startup, `ensureSuperAdmin()` (`server/src/platformAdmin.js`) creates or updates the one platform-admin account from three environment variables:
  ```bash
  SUPER_ADMIN_EMAIL=you@yourcompany.com
  SUPER_ADMIN_PASSWORD=a-strong-password-8-chars-or-more
  SUPER_ADMIN_NAME="Your Name"          # optional, defaults to "Super Admin"
  ```
  Set these before `npm start`/deploying the server. Leaving both email and password unset simply skips creating the account (fine for a dev server you're not using the console against); changing `SUPER_ADMIN_PASSWORD` and restarting the server rotates the password on the existing account rather than creating a second one.
- **Deliberately narrow scope.** Signed in at `admin.html`, you see every church in one searchable table (name, plan, member/staff counts, SMS status, created date) and can edit, per church: its **name, plan/subscription status, logo, motto, location, district, region**, and its **Arkesel SMS API key/sender ID**. That's the whole scope, on purpose — the console has no access to any church's members, finance, attendance, staff accounts or notices; that data stays exactly as private to each church as it is today. An edit you make here reaches that church's own devices the normal way, through their own next sync.

## Forgot password

The login screen's "Forgot password?" link (and the `/?resetToken=…` page it eventually leads to) emails a one-time reset link — until this existed, only an owner/admin could reset a colleague's password (Settings → Staff & leaders), which left an owner with no way back into their own account if *they* forgot it. The reply to a reset request is identical whether or not the email actually has an account, and never reveals which (`server/src/app.js`) — the same reasoning as the SMS/QR-check-in rate limiting below: nothing about the response should help someone probe who has an account here.

**How it's sent.** `server/src/email.js` posts to Brevo's transactional email HTTP API (`api.brevo.com`), over plain HTTPS — not SMTP. It was originally SMTP, via a small dependency-free client this project wrote itself, but Railway (and most PaaS hosts) blocks outbound SMTP ports (25/465/587) on every plan except its paid Pro tier, so that approach silently failed on a Free/Trial/Hobby Railway service: the connection attempt to Gmail never got anywhere. Brevo's API works over the same HTTPS port everything else in this app already uses, so nothing blocks it, and — unlike Resend, SendGrid, or most other REST-API providers — it lets you verify a single sender *address* (no custom domain or DNS records) for its free tier, which is why it's the one used here.

**Setup — a Gmail (or any) address works today, no domain needed:**
1. Create a free account at [brevo.com](https://www.brevo.com).
2. Under **Senders, Domains & Dedicated IPs → Senders**, add the address you want emails to come from and verify it — Brevo emails that address a confirmation link/code, no DNS setup required.
3. Under **SMTP & API → API Keys**, generate an API key.
4. Set these on the server:
   ```bash
   BREVO_API_KEY=xkeysib-...
   EMAIL_FROM=you@gmail.com                 # must be the address verified as a Brevo sender in step 2
   APP_URL=https://your-app-domain          # the hosted APP's URL, not the server's — this is what the emailed link points at
   EMAIL_FROM_NAME="The ChurchFlow"         # optional, this is the default
   ```
   Brevo's free tier caps out at 300 emails/day — plenty for a beta; a paid Brevo plan (or Railway's Pro tier plus the earlier SMTP approach) is worth revisiting before a large public launch.

Leaving `BREVO_API_KEY`/`EMAIL_FROM` or `APP_URL` unset doesn't break anything — "forgot password" requests still succeed (same generic reply either way), they just log an error server-side instead of actually emailing a link, exactly like any other unconfigured integration in this app (SMS, Paystack, WhatsApp).

## Architecture

## Architecture

```
 Phone app ─┐                          ┌──────────────────────────┐
 Desktop app┼─ local IndexedDB ─sync─▶ │ Server (per-church data) │
 Web/PWA   ─┘   (works offline)  ◀──── │ auth · roles · records   │
                                        └──────────────────────────┘
```

- **One codebase.** The client is plain HTML/JS modules (no build step). The same code is wrapped as a desktop app (Tauri or Electron) and phone apps (Capacitor), and also installs as a PWA.
- **Local-first.** Every read/write hits the device's database first, so nothing waits on the internet. Edits are marked *dirty* and pushed later.
- **Sync.** `POST /sync/push` sends dirty records; `GET /sync/pull?since=<cursor>` returns changes in server order. Conflicts are optimistic-concurrency by server-assigned version (`seq`), not by device clock: a write must be based on the version this device last saw, whoever commits first wins, and the loser's local copy is replaced with the winner's straight away. Deletes are tombstones so they propagate. Writes rejected for lack of permission are dropped locally rather than retried forever (fixed by Settings → Re-download data).
- **Multi-tenant.** Every row is keyed by `tenant_id` taken from the login token — never from the request. A device that signs in to a different church wipes its local data first.
- **Roles.** `owner`/`admin` (everything), `secretary` (members, attendance, messages), `treasurer` (finance), `leader` (only their ministries: members in it, its attendance, its finance entries, its updates). Enforced on the server in `server/src/permissions.js`; the app hides screens to match but is not the security boundary.

## Data model (collections)
`members` · `households` · `ministries` · `attendance` · `transactions` (tithe, offering, welfare, pledge payment, donation, expense; method incl. mobile money) · `messages` · `ministryUpdates`. Ministry-scoped records carry `ministryId` (members carry `ministryIds[]`). The `tenants` table (not a synced collection — server-side only) also holds `sms_api_key`/`sms_sender_id` for the Arkesel integration, `paystack_secret_key`/`paystack_public_key` for online giving, `whatsapp_phone_number_id`/`whatsapp_access_token`/`whatsapp_base_url`/`whatsapp_template_name`/`whatsapp_template_lang`/`whatsapp_checkin_service` for the WhatsApp integration, and `qr_checkin_service` for QR self-check-in. A separate, non-synced `giving_intents` table tracks each attempted online gift from checkout through confirmation (see below).

## Online giving (Paystack)

Settings → **Online giving** lets a church connect its own Paystack account (its own secret/public key pair — get them from paystack.com → Settings → API Keys & Webhooks) and share a giving link (`https://<your-app>/give.html?t=<tenantId>`) in Notices, WhatsApp, or the church bulletin. A donor opens that link, no login or app install required, picks an amount/purpose/ministry/fund, and pays by MTN MoMo, Telecel Cash, AirtelTigo, or card via Paystack's own checkout. **The money lands directly in that church's own Paystack account — The ChurchFlow never holds or moves it.**

**How it works.** `POST /give/init` (`server/src/app.js`) creates a `pending` row in `giving_intents` (amount, purpose, donor name/email/phone, which ministry/fund if any) and asks Paystack to start a checkout, using that church's own secret key (`server/src/paystack.js`). Paystack redirects the donor back to `give.html?reference=…` after checkout; that page polls `GET /give/status`, which — if still pending — asks Paystack directly whether the payment actually succeeded and, if so, posts an ordinary entry into the same append-only `transactions` ledger everything else uses (tagged `source: 'paystack'`, with the donor's name/contact in the note) and marks the intent `paid`. Paystack's own webhook (`POST /give/webhook`, HMAC-SHA512-signed per request with that church's secret key) is the durable backstop for a donor who pays but never makes it back to the browser (e.g. approves a MoMo prompt then closes the tab); both paths finalize the same way and are idempotent, so whichever arrives first wins and the other is a no-op.

**Recommended: add the webhook URL too.** The redirect-back flow above already finalizes most gifts on its own, but a donor who approves a MoMo prompt and then closes the browser before being redirected back would otherwise sit `pending` forever. In each church's own Paystack dashboard → Settings → API Keys & Webhooks, set the webhook URL to `https://<your-server>/give/webhook` — this is optional but closes that gap.

**Test it safely first.** Paste your Paystack **test** keys (`sk_test_…`/`pk_test_…`) under Settings before going live — Settings shows "test mode" clearly when they're in use, and Paystack's test cards/MoMo numbers work end to end without moving real money. Switch to live keys (`sk_live_…`/`pk_live_…`) once you're ready to accept real payments.

**Known limits of v1:** no automatic matching of an online gift to an existing member record (it's recorded with just the donor's name/email/phone in the note — reconcile manually, or ask donors to also register as members); no receipt email is sent (Paystack may send its own); one currency (GHS) and one designated fund/ministry per gift.

## WhatsApp (broadcast + check-in)

Settings → **WhatsApp** lets a church connect its own WhatsApp Business API access — a phone number ID + access token, either straight from Meta (developers.facebook.com, after completing Meta Business Verification for the church) or through a Business Solution Provider such as Arkesel acting as the go-between. This is the same "bring your own account" pattern as SMS and Paystack above: the access token is stored server-side only on that church's own tenant row and never reaches a device's local IndexedDB store, and The ChurchFlow never sends on a church's behalf through a shared number — so there's no per-message cost or Meta compliance burden on Joey Studios, only setup friction per church (Meta Business Verification is a real, sometimes multi-day process; see "Known limits" below).

**Setup.** In Settings → WhatsApp, enter the phone number ID and access token from Meta (or from the BSP's dashboard, which usually issues the same two values), plus the name and language of the one WhatsApp message template approved for this church (see "Templates" below) and, optionally, what to call the attendance record a check-in reply creates (defaults to "Sunday service"). A "custom API base URL" field is tucked under an Advanced/collapsed toggle for a BSP that proxies Meta's API at its own address instead of `graph.facebook.com` directly.

**Sending a broadcast.** Posting a Notice (owner/admin/secretary) now offers "Also send as a WhatsApp broadcast" alongside the existing SMS checkbox, with the same whole-church-or-specific-ministries target picker (`POST /whatsapp/send`, `server/src/app.js`). Each recipient's stored phone number is normalized the same way SMS numbers are (`normalizeGhanaPhone`, reused from `server/src/sms.js`) and de-duplicated per shared household number.

**Templates — why a broadcast needs one.** Outside a 24-hour window from a recipient's own last message to the church's number, Meta requires an outbound WhatsApp message to use a pre-approved template rather than free text. A church only needs to get *one* simple template approved, once, in Meta Business Manager: a single body variable (e.g. named `church_notice`, body `{{1}}`) — every future broadcast just fills that one variable with the notice's own text, so nothing needs re-approving per notice.

**Check-in by reply.** A member replies **IN** (also recognized: HERE, PRESENT, CHECK IN, CHECKIN — case-insensitive) to the church's WhatsApp number; the sender's WhatsApp number is matched to a member the same way SMS numbers are, and if found, that member is marked present on today's whole-church attendance record (creating one, named by the configured "check-in service" setting, if today doesn't have one yet). It's idempotent — replying twice doesn't double-count — and the member gets an automatic confirming reply either way ("You're checked in for today" / "You're already checked in"); a number that doesn't match any member gets no reply at all, so a wrong number can't be used to probe who's a member. This reply is sent as free text (not a template), which is always allowed since it's a direct reply within the 24-hour window.

**How the webhook is wired up.** In the church's Meta App (or the BSP's dashboard) → WhatsApp → Configuration, set the webhook URL to `https://<your-server>/whatsapp/webhook` and the verify token to whatever `WHATSAPP_VERIFY_TOKEN` is set to on the server (one shared value for the whole app, not per-church — it only proves this server owns the endpoint; an inbound message is routed to the right church afterwards by matching the `phone_number_id` in Meta's payload against that church's own stored phone number ID). Meta calls this URL once with a `GET` handshake when it's first saved (`verifyWebhookChallenge` in `server/src/whatsapp.js`) and then with a `POST` for every inbound message after that.

**Known limits of v1:** Meta Business Verification is a real per-church hurdle — expect it to take from same-day to several business days, which is why WhatsApp is opt-in and separate from SMS rather than a replacement for it. The inbound webhook does not verify Meta's HMAC request signature (unlike the Paystack webhook, which does, since actual money is at stake there) — acceptable for attendance data but worth adding before handling anything higher-stakes over the same channel. Only text-message replies are handled (status updates, media, and button/list replies are ignored); only whole-church check-in is supported, not per-ministry.

## QR self-check-in

Settings → **QR check-in** shows a QR code and a copyable link for this church's own public check-in page — display it on a screen or tablet at the entrance, or print it, and members scan it with their own phone's camera app (no app install, no account, and unlike WhatsApp check-in, no Meta Business Verification or any third-party setup at all — it's available to every church immediately). Scanning it opens `app/checkin.html?t=<tenantId>`, where a member types the phone number on their own member record and taps "Check in". A phone that matches a member marks them present on today's whole-church attendance record — the exact same mechanism WhatsApp's "IN" reply uses (`recordSelfCheckIn` in `server/src/app.js`), so it's idempotent (scanning twice doesn't double-count) and creates the record if today doesn't have one yet, named by Settings' "Default check-in service name" (falling back to the WhatsApp check-in service name, then "Sunday service", if left blank). A phone that doesn't match anyone is told to see the welcome desk — the public page never reveals who is or isn't a member.

**No npm package for the QR code.** The client has no build step (see "Architecture" below), so there's nothing to `npm install` at runtime — instead `app/js/vendor/qrcode.js` is a small, dependency-free QR encoder written for this app. It deliberately covers only what a check-in link needs (byte-mode text, error-correction level L, symbol versions 1–6, so no check-in URL should ever come close to its ~134-byte ceiling) rather than the full QR specification. Because a hand-written encoder can't be sanity-checked just by reading the code, it was verified by rendering its output to a bitmap and decoding it back with an independent, unrelated decoder (OpenCV) across versions 1–6 and the exact byte-length boundaries between them, confirming every one reproduces the original text exactly.

**Known limits of v1:** one phone number checks in one member — no way to check in a household in one scan. (The public check-in page *is* rate-limited per IP — see "Server hardening" below — but a determined attacker rotating IPs could still grind through guesses slowly; the "not found" response itself still gives no information back either way.)

## Hikvision clock-in integration

If attendance is taken with a Hikvision face/fingerprint/card terminal, `server/hikvision-bridge.js` pulls its check-in events and records them as attendance automatically — no changes to the app itself, it's just another way attendance gets recorded besides the manual "Take attendance" screen.

**How it works.** Hikvision terminals speak a standard integration protocol called ISAPI over plain HTTP on the local network. The bridge script runs on a computer on that same network (it does *not* need to be the same machine running the ChurchFlow server, as long as it can reach both), polls the device for new check-in events every 30 seconds by default, matches each event to a member by a "Clock-in device ID" you set once per member, and posts attendance the same way the browser app does — reusing the exact same sync client (`app/js/sync.js`), so it gets the same optimistic-concurrency and permission handling for free. Re-polling never double-counts someone: the event window only moves forward, and adding an already-present member to an attendance record is a no-op.

**Setup:**
1. In The ChurchFlow, **Staff → Add account**, create a login for the bridge to use (role `secretary` is enough — it can write attendance). Don't reuse a real person's login.
2. In **Members**, open each enrolled member and set **Clock-in device ID** to their person/employee number on the terminal (this is whatever ID number the terminal itself assigns them when they're enrolled with their face/fingerprint — check the terminal's own admin screen or its bundled configuration software for that number).
2b. In **Ministries**, open each ministry that has its own clock-in-tracked gathering (a choir practice, a youth meeting…) and set **Meets on** to the day(s) it meets — see "Which service or ministry a check-in counts toward" below for why this matters.
3. Copy `server/hikvision.config.example.json` to `server/hikvision.config.json` and fill in the device's IP address (find it on the terminal's own network settings screen) and admin credentials, the ChurchFlow server address, and the bridge account's login.
4. Run it:
   ```bash
   node server/hikvision-bridge.js --probe   # dumps the device's raw events first — see below
   node server/hikvision-bridge.js            # polls continuously (leave running during services)
   node server/hikvision-bridge.js --once     # a single poll, for running from cron instead
   ```

**Please verify with `--probe` before relying on it.** The event field names this script expects (`employeeNoString`, `time`, …) follow Hikvision's publicly documented ISAPI schema and are consistent across most of their access-control/time-attendance terminals, but firmware does vary a little by model. `--probe` fetches today's raw events from your actual device and prints them without touching The ChurchFlow at all — have someone clock in, run it, and send me that output if anything looks different from what's in `server/src/hikvision.js` (`parseAcsEvents`) so the field mapping can be adjusted for your exact model.

**Which service or ministry a check-in counts toward.** A shared clock-in terminal has no way to know *which* gathering someone actually walked into, so every check-in in a given poll is attributed by calendar day, using the same rule for both this live bridge and the CSV device-log upload below: a check-in on a Sunday always counts toward the whole church's main Sunday service (its name comes from `"servicesByDay": {"sunday": "..."}` in the config, or `"Sunday service"` if that's not set); a check-in on any other day is attributed to whichever ministry has that day in its own **Meets on** schedule (Ministries → open a ministry → Edit); and a check-in on a day where *no* ministry meets isn't recorded at all — there's nothing to attribute it to, so it's silently skipped rather than filed under a guess (the live bridge logs the skip to the console; the CSV upload reports a skipped-day count in its toast). If two ministries happen to meet on the same day, one is picked automatically (alphabetically by name) rather than double-counting the check-ins under both or dropping the day. This logic lives in `app/js/importers.js`'s `attendanceTargetForDay`, shared by both import paths. A device ID that doesn't match any member is logged to the console (live bridge) or listed in the toast (CSV upload) so the office can fix it, but doesn't block anyone else's check-in from being recorded.

The **Attendance** page itself also has filter tabs above its table — "All" plus one tab per day of the week (Sunday, Monday, …) — for viewing (and exporting) just that day. Only days that actually have attendance recorded get a tab, so a church that never records anything on, say, Wednesday or Saturday just sees the days it does use; a tab appears on its own the moment something is first recorded on that day. Which tab a record falls under is read straight off its own date (the same `dayNameFor` calendar check as above), never off what its service name happens to say — a record someone manually typed "Sunday service" into still lands under whatever its date's actual weekday is.

**Running it unattended (macOS background service).** Typing `node server/hikvision-bridge.js` and leaving a Terminal window open works, but it stops the moment that window closes or the Mac restarts. To have it start on its own and keep running:
1. Find node's install path: `which node` in Terminal.
2. Copy `server/com.churchflow.hikvision-bridge.plist.example` to `server/com.churchflow.hikvision-bridge.plist` (gitignored — it bakes in this machine's own paths) and fill in the three placeholders: node's path from step 1, and this checkout's absolute folder path (wherever `church-app` lives on this Mac) wherever it appears.
3. Install and start it:
   ```bash
   cp server/com.churchflow.hikvision-bridge.plist ~/Library/LaunchAgents/
   launchctl load ~/Library/LaunchAgents/com.churchflow.hikvision-bridge.plist
   ```
   It's now running, and will start again automatically every time this Mac logs in — no need to open a Terminal or remember to start it before a service.
4. Check on it any time: `tail -f server/hikvision-bridge.log` (and `hikvision-bridge.error.log` if something's wrong).
5. To stop it (e.g. before changing `hikvision.config.json`): `launchctl unload ~/Library/LaunchAgents/com.churchflow.hikvision-bridge.plist`, make the change, then `launchctl load` again to restart it.

This machine must stay powered on and connected to the same network as the clock-in device whenever attendance should be captured — a laptop that's closed or asleep, or off the church's WiFi, can't poll the device. See "Doing this at the church" below for what that means in practice.

**Doing this at the church.** The bridge only works while it's running on a computer that's on the *same local network* as the clock-in device — it can't reach the device over the internet. In practice that means: bring (or permanently keep) a computer at the church, join it to the same WiFi/network the terminal is on, and either leave a Terminal window open running the bridge during the service, or set it up as the background service above so it's always on. If the church's network is different from wherever the device was tested (a different WiFi network has a different address range), check the device's IP again from its own network settings screen once it's on the church's network, and update `"host"` in `hikvision.config.json` to match — a DHCP reservation on the church's router keeps that address from changing later.

If keeping a computer running continuously at the church isn't practical, there's a simpler manual alternative that needs no background service and no network reachability at all beyond a one-time file transfer: the device's own web interface (or its bundled configuration software) can export its full check-in log as a CSV file (often named something like `recordListAutoRecovered_*.csv`). Uploading that file in the app's **Attendance** page (the "Upload attendance spreadsheet" card) is recognized automatically as a Hikvision device log and imports one attendance record per day it covers — it can even create member records for anyone the device recognizes who isn't registered yet, and backfills Clock-in device IDs for existing members matched by name. This is the "do it after the fact, no live bridge needed" option; the live bridge above is the "attendance shows up automatically, in real time" option. They're not mutually exclusive — the manual upload is also a good way to backfill history from before the bridge was set up.

### Pulling the device's enrolled-user list, as a spreadsheet to review

Separately from the bridge above (which pulls *check-in events*), Settings → **Clock-in device** → "Pull enrolled users from device" pulls the device's *enrolled* name/person-ID list — the roster it already knows, from however it was enrolled (face/fingerprint/card) — so the office can turn it into member records without retyping names.

**How it works.** `app/serve.js` (the same small Node process that serves the app itself) exposes one same-origin route, `POST /api/device/pull-users`. Because `serve.js` runs on the church's own computer, on the same local network as the terminal (the hosted sync server generally can't reach a church's LAN device, but this one already does), it can call straight into `server/src/hikvision.js`'s ISAPI client — reusing the same digest-auth request helper and `server/hikvision.config.json` the bridge uses (copy `server/hikvision.config.example.json` if you haven't already; only the `device` section is needed for this feature). The route returns each enrolled person's number and name as JSON; the browser turns that into a `.csv` file (Name, Device ID prefilled; Phone, Email, Gender, Status, Birthday, Household left blank) and downloads it straight away — **it never creates a member by itself.**

**Review, then upload it back in.** Open the downloaded file in Excel, fill in whatever the device doesn't know (phone, status, birthday, household…), and save it. Then go to **Members → Upload member spreadsheet** and pick that same file: it creates a new member for each row that doesn't match anyone yet, and fills in fields (without blanking out anything already on file) for a row that matches an existing member — by Device ID first, then by exact name. See "Member and attendance spreadsheet uploads" below for the matching rules in full.

**Please verify against your device.** As with `AcsEvent` above, the field names this expects (`employeeNo`, `name` from `POST /ISAPI/AccessControl/UserInfo/Search`) follow Hikvision's publicly documented ISAPI schema but firmware varies a little by model — if the "Pull enrolled users" button reports an error or the names/IDs look wrong, check the response your device actually sends (e.g. with `curl --digest -u admin:pw -d '{"UserInfoSearchCond":{"searchID":"1","searchResultPosition":0,"maxResults":30}}' http://<device-ip>/ISAPI/AccessControl/UserInfo/Search?format=json`) and adjust `parseUserInfoSearch` in `server/src/hikvision.js` if it differs.

### Member and attendance spreadsheet uploads

Two more places accept a spreadsheet, both plain `.csv` (opens natively in Excel — no binary spreadsheet format, so no extra library):

- **Members → Upload member spreadsheet.** Same column shape as the device-pull export: `Name, Device ID, Phone, Email, Gender, Status, Birthday, Household` (headers matched case-insensitively; only `Name` is required). Each row is matched to an existing member by Device ID first (if the row has one and it matches a member's stored device ID), then by exact case-insensitive name, otherwise a new member is created. Only the columns a row actually fills in are written — a blank cell never erases existing data. A new household name is created automatically if it doesn't already exist. Afterwards a toast reports how many were created vs. updated (and how many rows were skipped for having no name).
- **Attendance → Upload attendance spreadsheet.** A bare "who was present, for one date" list, not a historical clock-in-log importer: pick a date (defaults to today) and a spreadsheet with one column of either names or clock-in device IDs, with or without a header row. Each entry is matched the same way (device ID, then case-insensitive name) and folded into that date's attendance record (adding to it, not replacing names already ticked another way). A toast reports how many were marked present and lists any entries that didn't match a member, so staff can fix the spreadsheet or the member record.

The parsing/matching logic behind all three uploads (`app/js/csv.js`, `app/js/importers.js`) is plain, dependency-free, unit-tested functions kept separate from the screen code — see `app/test/csv.test.js` and `app/test/importers.test.js`.

## Server hardening

Every login and public-facing endpoint is rate-limited per IP address (`server/src/app.js`): 10 attempts/minute for `/auth/login` and `/admin/login`, 5/minute for new church registration, and 20/minute for the public `/checkin` and `/give/init` endpoints. A client past its limit gets a `429` with a plain "too many attempts, please wait a moment" message rather than being blocked silently or forever — this closes off both password-guessing and the phone-number-enumeration surface the public check-in page would otherwise expose. See `server/test/ratelimit.test.js` (4 tests) for the exact behavior, including that limits are tracked independently per IP so one client's burst never affects another's.

Passwords are hashed with `scrypt` and a per-user random salt, never stored or compared in plain text; login tokens are HMAC-signed and expire after 30 days (`server/src/auth.js`). Both password verification and token-signature checks use a constant-time comparison to avoid timing attacks.

**Still open, tracked in "Known limits" below:** encryption at rest for the SQLite database file itself, and backups beyond Render's built-in daily disk snapshots (7-day retention) — worth revisiting before the database holds a meaningful number of churches' data.

## Deploying

`render.yaml` at the repo root is a [Render Blueprint](https://render.com/docs/blueprint-spec) defining two services from this one repo: a Web Service for `server/` (the API, with a persistent disk for `church.db`) and a Static Site for `app/` (served as-is, no build step). To deploy:

1. Push this repo to GitHub.
2. In the Render dashboard, **New → Blueprint**, point it at the repo. Render reads `render.yaml` and creates both services.
3. Open the Web Service's **Environment** tab and fill in the secrets left blank in `render.yaml` (`JWT_SECRET`, `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD`, and `WHATSAPP_VERIFY_TOKEN` if using WhatsApp) — these are intentionally not committed to git.
4. Once the Web Service is live, copy its URL (e.g. `https://church-manager-server.onrender.com`) into `PRODUCTION_API_URL` in `app/js/config.js`, commit, and push — the Static Site auto-redeploys and the deployed app will now talk to the deployed API instead of `localhost:8787`.
5. A custom domain can be added to the Static Site afterwards from Render's dashboard (Settings → Custom Domains) once one is registered.

Render's paid disk tier includes automatic daily snapshots (7-day retention) as a baseline backup — see "Server hardening" above for what's still open beyond that.

## Known limits to fix before real churches use it
1. ~~Conflict resolution is last-write-wins by edit time.~~ **Fixed in v0.5:** conflicts are now resolved by a server-assigned version (`seq`), never by comparing device clocks. See `server/src/app.js` (`POST /sync/push`) and the "server-assigned versions" tests.
2. ~~Finance entries can be edited or deleted.~~ **Fixed in v0.5:** the ledger is append-only for every role, including owner/admin — a posted transaction can never be mutated (`server/src/permissions.js` + `app.js`). Corrections and reversals post new entries linked by `reverses`/`correctsId`; still worth adding a dedicated audit-log view and month-end locking later.
3. **Local data is not encrypted at rest**; the login token lives on the device. Add device PIN/biometrics and encrypted storage in the phone/desktop builds.
3a. **Desktop builds are unsigned.** Fine for a pilot church testing on their own machine (with one click through the OS's "unknown developer" warning), but a real Apple Developer certificate (~$99/year) and a Windows code-signing certificate are needed before distributing this more widely, so the warning goes away.
4. **SQLite → Postgres** for the hosted server, plus HTTPS (handled automatically by Render), email verification, and backups beyond Render's built-in daily disk snapshots. ~~Rate limiting.~~ **Fixed:** see "Server hardening" above. ~~Password reset by email.~~ **Fixed:** see "Forgot password" above.
5. **Tokens last 30 days.** Deactivating a staff account locks them out on their next request, but their device keeps its local copy until signed out (Settings → Re-download data refreshes what a user may see).
6. **Data protection.** Member data is personal data and giving records can reveal religious belief: consent, privacy policy, Data Protection Commission registration (Ghana Act 843) and a data-processing agreement with each church.
7. **Rejected offline edits due to a permission change** (e.g. a leader editing outside their ministry) are reported by a warning; the local copy is corrected by "Re-download data". (A version conflict — including an attempted edit of a posted finance entry — now self-heals immediately instead, no re-download needed.)
8. **Spreadsheet-upload name matching can misfire on duplicate names.** Member and attendance uploads match a row to an existing member by Device ID first, then by exact case-insensitive name — two members who happen to share a name (e.g. a parent and child both "Ama Mensah") will match whichever one the lookup finds, silently. Setting a Device ID on both is the reliable fix; otherwise review the "N created, M updated" summary after an upload before trusting it.
9. **`POST /api/device/pull-users` only exists on `app/serve.js`**, the plain local dev/production static server — it assumes the church runs this app from a computer on the same network as the clock-in device (see "Hikvision clock-in integration"). It has no equivalent yet in a wrapped desktop/phone build or if the app is ever served some other way.

## Desktop app (Mac + Windows)

`src-tauri/` wraps the exact same client (`app/`) in a native window using [Tauri](https://tauri.app) — there's no separate offline mode to build or maintain, because the web app is already local-first (IndexedDB + `app/js/sync.js`): it works fully offline and syncs to the hosted server the moment a connection is available, whether it's running in a browser tab or as an installed desktop app. The desktop shell adds nothing except a native window, icon, and installer — no bundled local server.

**Building it.** Neither a cloud sandbox nor a typical dev machine can produce a genuine signed macOS *and* Windows build from one place — a real Mac build needs a real Mac, a real Windows build needs a real PC. So this repo's `.github/workflows/desktop-build.yml` builds both using GitHub's own hosted `macos-latest` and `windows-latest` runners:

1. Push this repo to GitHub (already done — see "Deploying" above for the same repo).
2. Go to the repo's **Actions** tab → **Build desktop app (Mac + Windows)** → **Run workflow**.
3. Once it finishes (~10–15 minutes), open the completed run and download the **Artifacts** — a `.dmg` (Mac) and an `.msi`/`.exe` installer (Windows).

**Unsigned, for now.** These builds aren't code-signed with an Apple Developer or Windows signing certificate (both require a paid account), so macOS will show an "unidentified developer" warning (right-click → Open, once, to bypass) and Windows Defender SmartScreen may show an "unknown publisher" prompt (More info → Run anyway). This is normal for an early/internal build and fine for testing with a pilot church; add real signing before wider distribution — see "Known limits" below.

**Icon.** `src-tauri/icons/` holds a placeholder icon generated from the app's own sidebar glyph and brand colors (`#0d2b27` / `#f4f7fc` from `app/manifest.webmanifest`) — swap these files for real branding whenever Joey Studios has one ready; `tauri.conf.json`'s `bundle.icon` list is where they're referenced.

**Phone (not started yet):** the same wrapping approach would work with Capacitor instead of Tauri — `npm i @capacitor/core @capacitor/cli`, `npx cap init`, set `webDir` to `app/`, `npx cap add android ios`, build in Android Studio / Xcode. Swap IndexedDB for SQLite (`@capacitor-community/sqlite`) if a single device is expected to hold more than ~50k records.
